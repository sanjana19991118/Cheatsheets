Database Concepts: RDBMS vs. Non-RDBMS

Understanding the fundamental difference between these storage systems is essential for architecting scalable applications (e.g., using AWS services).

1. Data Modeling

RDBMS (Relational)

Data stored in Tables (Rows/Columns). Strict schema.

| ID | Name | Age |
|----|------|-----|
| 1 | Bob | 25 |

Example: Amazon RDS

NoSQL (Non-Relational)

Data stored as Documents, Key-Value, or Graphs. Flexible schema.

{ "id": 1, "name": "Bob", "meta": {...} }

Example: Amazon DynamoDB

2. Deep Dive: ACID (RDBMS Core)

[Image of ACID database transactions concept]

ACID is the reliability standard for RDBMS transactions:

  • Atomicity: "All or nothing." If one part of a transaction fails, the whole thing is rolled back.
  • Consistency: Transactions take the database from one valid state to another valid state (enforcing all rules/constraints).
  • Isolation: Transactions occurring simultaneously don't interfere with each other.
  • Durability: Once a transaction is committed, it stays committed, even if the system crashes.

3. Deep Dive: CAP Theorem (NoSQL Trade-off)

[Image of CAP theorem in distributed systems]

Distributed systems cannot simultaneously guarantee all three, so they must pick two:

  • Consistency (C): Every read gets the most recent write.
  • Availability (A): Every request receives a (non-error) response.
  • Partition Tolerance (P): The system continues to operate despite network failures.

NoSQL databases (like DynamoDB) often prioritize AP or CP, whereas RDBMS focuses on CA (within a single node) or requires complex configuration for distribution.
