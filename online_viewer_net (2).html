System Design

Interviewer: A WhatsApp group has 978 members. You send one message. Is it 1 database write or 978 writes?

Short Answer: From a storage/persistence perspective, it is 1 database write, but from a networking and distribution (fan-out) perspective, it triggers 978 downstream delivery operations.

Deep Dive: How WhatsApp Handles This

  • The Write Operation (1 Database Write): When sending a message to a group, the client sends a single request to the server. The server writes that message into the chat history storage once, rather than duplicating it across 978 individual user inboxes in a traditional relational database.
  • The Fan-Out Delivery Mechanism: Once stored, the system uses a fan-out model (leveraging high-concurrency systems like Erlang processes) to route the message packet to active user sockets or queue it for offline members.
How to Answer in an Interview: "It depends on whether you mean database persistence or delivery processing. For persistence, it is 1 database write. For distribution/fan-out, the system handles 978 delivery paths to route the message to all active group sessions."
Version Control / Git

Interviewer: Your local branch is behind the remote branch. Would you use git pull or git fetch, and why?

Short Answer: You should use git fetch first as a best practice to inspect changes safely, though git pull combines fetching and merging into a single automated step.

Deep Dive: The Difference and Why It Matters

  • git fetch (The Safe Approach): Downloads remote changes into your local repository's remote-tracking branches (e.g., origin/main) without modifying your working branch. This lets you inspect changes safely using git diff or git log before merging.
  • git pull (The Shortcut): Automatically runs git fetch followed immediately by a merge into your current working branch. While faster, it can surprise you with unexpected merge conflicts directly in your workspace.
How to Answer in an Interview: "I would use git fetch first because it's safer. It downloads remote changes so I can inspect them with git diff before integrating. git pull automates both fetching and merging, which is faster but can introduce unexpected conflicts if upstream changes haven't been reviewed."
System Design / Caching

Interviewer: Your Redis cache suddenly goes down. How would you ensure your application stays available without overwhelming the database?

Short Answer: To keep your application available without crushing the database during a Redis outage, you need a multi-layered defense strategy: Circuit Breaking, Local In-Memory Caching (L1), Graceful Degradation (Stale-While-Revalidate), and Database Load Shedding/Rate Limiting.

Deep Dive: How to Handle a Redis Outage Gracefully

  • 1. Circuit Breaker Pattern: Implement a circuit breaker (using libraries like Resilience4j or Polly). When Redis throws continuous connection errors or timeouts, the circuit "trips" and opens. Instead of every single request continuing to hammer a dead cache server and timing out, the application instantly stops trying to reach Redis for a configured cooldown period, failing over directly to safety measures.
  • 2. Local In-Memory Cache (L1 Cache): Maintain a small, short-lived fallback cache directly inside the application node's memory (e.g., using Guava Cache, Node-Cache, or a simple LRU dictionary) for ultra-hot data. If Redis goes down, your app can serve hot reads from local memory instead of routing every request down to the persistent database.
  • 3. Graceful Degradation & Stale Data (Stale-While-Revalidate): If the primary data source or remote cache fails, configure your application to return stale/default data or static fallback responses rather than throwing a hard 500 Internal Server Error. Users prefer seeing slightly outdated data over an entirely broken application or a loading spinner that never finishes.
  • 4. Rate Limiting and Load Shedding: Protect your database from a massive "thundering herd" effect by implementing rate limits or request queues on incoming traffic. If thousands of concurrent requests suddenly bypass the dead cache and hit the database simultaneously, the database will lock up or crash. Shedding excess load keeps the core database alive.
How to Answer in an Interview: "If Redis goes down, the biggest risk is a thundering herd crashing the database. To prevent this, I would use a Circuit Breaker to quickly stop calls to the dead cache, fall back to a local in-memory (L1) cache or stale data for critical reads, and apply rate limiting to shed excess traffic so the database doesn't get overwhelmed."
